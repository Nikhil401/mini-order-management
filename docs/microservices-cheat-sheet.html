Mini Order Management Microservices Cheat Sheet

A compact summary of the full learning project: .NET microservices, Docker, Docker Compose, Kubernetes, config, health checks, scaling, and logging.

InventoryService OrderService Docker Kubernetes ConfigMap Secret Health Checks Structured Logging

What We Built

  • InventoryService with in-memory products and GET endpoints.
  • OrderService with in-memory orders and POST/GET endpoints.
  • HTTP communication from OrderService to InventoryService using typed HttpClient.
  • Docker images for both services.
  • Docker Compose for local multi-container development.
  • Kubernetes manifests for Pod, Deployment, Service, ConfigMap, Secret, probes, and scaling.

Core Mental Model

Dockerfile = how to build one container image.
docker-compose.yml = how to run and connect multiple containers locally.
Pod = the running unit in Kubernetes.
Deployment = keeps the desired number of Pods alive.
Service = stable network name in front of Pods.
ConfigMap / Secret = runtime configuration injected into Pods.

Request Flow

One create-order request travels like this:

Browser or Invoke-RestMethod
OrderService endpoint
OrderService calls InventoryService through Kubernetes Service DNS
InventoryService returns product data
OrderService validates stock and creates the order
Response goes back to the caller

Important URLs

  • http://localhost:5001/api/inventory
  • http://localhost:5002/api/orders
  • http://localhost:5001/health
  • http://localhost:5002/health

These work when the relevant service is exposed through Docker Compose or kubectl port-forward.

Kubernetes Summary

  • Pod: runs the container.
  • Deployment: manages replicas and self-healing.
  • Service: gives stable internal access.
  • ClusterIP: internal-only service type used for service-to-service calls.
  • port-forward: temporary way to access the app from your laptop.

Configuration Summary

  • ConfigMap: non-sensitive settings, like InventoryService__BaseUrl.
  • Secret: sensitive values, injected separately from normal config.
  • envFrom: loads all keys from a ConfigMap or Secret into environment variables.

Health Checks

  • Readiness: can this Pod receive traffic?
  • Liveness: should this container be restarted?
  • /health endpoint: simple application health signal.
readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10

Logging Summary

  • Structured logs were added to trace the request path.
  • Logs include product id, quantity, order id, and trace id.
  • Useful for following one request across both services.

You now have a working learning project that demonstrates the full path from a simple ASP.NET Core API to containerization, multi-service communication, Kubernetes deployment, scaling, config management, probes, and logging.

How To Run The Project

This is the practical startup sequence from a fresh machine to a working local and Kubernetes setup.

1. Install the prerequisites

  • .NET 10 SDK - builds and runs the ASP.NET Core services.
  • Docker Desktop - builds and runs the containers locally.
  • Kubernetes enabled in Docker Desktop - runs the cluster on your machine.
  • Kubectl - sends commands to Kubernetes.

2. Open the project folder

Open PowerShell in:

C:\Users\HP\Desktop\Learning Microservices

Purpose: all commands below assume you are in the project root.

3. Build and run locally with .NET

dotnet build MiniOrderManagement.slnx
dotnet run --project src/InventoryService
dotnet run --project src/OrderService

Purpose: verify the apps compile and run before using containers.

4. Test the APIs locally

Invoke-RestMethod http://localhost:5001/api/inventory
Invoke-RestMethod http://localhost:5002/api/orders

Purpose: confirm each API responds from your machine.

5. Build the Docker images

docker build -t mini-orders/inventory-service:step7 -f src/InventoryService/Dockerfile .
docker build -t mini-orders/order-service:step7 -f src/OrderService/Dockerfile .

Purpose: package each service into a portable image.

6. Run with Docker Compose

docker compose up --build

Purpose: start both services together and let them talk through Docker networking.

7. Test Docker Compose endpoints

Invoke-RestMethod http://localhost:5001/api/inventory
Invoke-RestMethod -Method Post -Uri http://localhost:5002/api/orders -ContentType application/json -Body '{"productId":101,"quantity":2}'

Purpose: confirm the services can communicate through Compose.

8. Enable Kubernetes in Docker Desktop

  • Open Docker Desktop.
  • Go to Kubernetes settings.
  • Enable Kubernetes and wait for it to become active.

Purpose: prepare the local cluster for the Kubernetes steps.

9. Apply the Kubernetes manifests

kubectl apply -f k8s/inventory-deployment.yaml
kubectl apply -f k8s/inventory-service.yaml
kubectl apply -f k8s/order-configmap.yaml
kubectl apply -f k8s/order-secret.yaml
kubectl apply -f k8s/order-deployment.yaml
kubectl apply -f k8s/order-service.yaml

Purpose: create the workloads, Services, and config objects inside the cluster.

10. Verify the cluster

kubectl get deployments,svc,pods
kubectl rollout status deployment/inventory-deployment
kubectl rollout status deployment/order-deployment

Purpose: confirm the cluster is healthy and the Deployments have rolled out.

11. Port-forward for browser access

kubectl port-forward service/inventory-service 5001:8080
kubectl port-forward service/order-service 5002:8080

Purpose: expose internal ClusterIP Services to your laptop for local testing.

12. Run the final tests

Invoke-RestMethod http://localhost:5001/health
Invoke-RestMethod http://localhost:5002/health
Invoke-RestMethod -Method Post -Uri http://localhost:5002/api/orders -ContentType application/json -Body '{"productId":101,"quantity":2}'

Purpose: verify health checks, routing, and service-to-service communication.

If something fails, check the logs with kubectl logs -f <pod-name> and compare the result with the expected request path.

What Each File Does

This section explains the repository in the order you usually think about it: build one app, connect both apps, then run them in Kubernetes.

Dockerfile in each service

  • InventoryService/Dockerfile builds the Inventory API into one container image.
  • OrderService/Dockerfile builds the Order API into one container image.
  • Each Dockerfile says how to restore, build, publish, and run one .NET app.

Purpose: turn one source project into one reusable image.

docker-compose.yml

  • Starts both containers together on your local machine.
  • Connects the services through Docker networking.
  • Maps local ports like 5001 and 5002 to container port 8080.

Purpose: run the whole mini system locally with one command.

k8s folder

  • inventory-deployment.yaml = keeps InventoryService Pods running.
  • inventory-service.yaml = gives InventoryService a stable internal address.
  • order-deployment.yaml = runs OrderService and injects config, secret, and probes.
  • order-service.yaml = gives OrderService a stable internal address.
  • order-configmap.yaml = stores non-sensitive runtime config.
  • order-secret.yaml = stores a secret value separately from code.
  • inventory-pod.yaml = the basic single Pod example used earlier for learning.

Purpose: describe the same app in Kubernetes terms.

Animated Flow In Words

Think of the project as a sequence of stages that hand work to the next stage.

1. Source code exists in each service folder.
2. Dockerfile turns that source code into a container image.
3. docker-compose.yml starts both images together and connects them locally.
4. Kubernetes manifests define the same services for the cluster.
5. ConfigMap and Secret inject runtime values into the OrderService Pod.
6. Deployment keeps the right number of Pods alive and replaces failed ones.
7. Service gives a stable DNS name so OrderService can call InventoryService.
8. Health checks and probes tell Kubernetes whether the Pods are ready and alive.
9. Logs show the request path when you send an API call.
